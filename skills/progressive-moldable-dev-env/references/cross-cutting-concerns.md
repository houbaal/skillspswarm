# Cross-Cutting Concerns

## View Generation with AI Agents

Views are infrastructure generated by AI agents (Claude Code or similar). This means:
- Language verbosity for views matters less than traditionally assumed
- The human invests thinking in **what to inspect and how entities relate** (data model design)
- The human does NOT need to understand view implementation details
- Views can be regenerated, modified, or discarded freely
- The speed difference between generating a Go template vs Ruby ERB vs JSX is negligible with AI assistance

The practical workflow: describe what you want to see in natural language, the AI agent generates the view, you look at the output, you iterate ("show me only the ones with circular dependencies", "add a column for test coverage") or discard and try a different angle. The generation cost is near zero. The iteration cycle is seconds.

## Zoom Levels & Representation Diversity

### Three Zoom Levels

Every inspectable aspect of your system should be approachable at three levels:

| Level            | What It Shows                                         | Example Forms                                                                   |
|------------------|-------------------------------------------------------|---------------------------------------------------------------------------------|
| **High-level**   | Big picture, system shape, overall health             | One-liner verdicts, single metrics, traffic-light indicators, executive summary |
| **Medium-level** | Module/component relationships, patterns, trends      | Tables, dependency graphs, narrative summaries, metric dashboards               |
| **Low-level**    | Individual entities, specific code paths, raw details | AST dumps, full entity JSON, line-by-line annotations, call traces              |

The environment should **guide navigation between these levels**. A red indicator at the high level should be clickable to reveal the medium-level view that explains why it's red.

### Representation Diversity

Graphs and tables are the obvious outputs. But understanding often comes from less conventional forms. The list below is a handful of examples — the whole point of moldable development is that *you* invent the representations that fit *your* specific context.

- **Question-driven views** — "Is this module coupled to the database?" -> "Yes: 14 direct SQL queries across 6 files."
- **Narrative summaries** — Prose that synthesizes what the data says.
- **One-liners** — "Payment: 12 deps, 3 circular, 0% test coverage on new code."
- **Condensed digests** — The 5 things you need to know about this module today.
- **Actionable metrics** — "Coupling score: 0.87 (threshold: 0.60)" — tied to decisions.
- **Diff views** — Structural diff: "Last week 3 dependencies, now 7. Here are the 4 new ones."
- **Comparative views** — "Module A vs Module B: cohesion, coupling, test coverage, change frequency."
- **Heatmaps** — File change frequency, temporal coupling, complexity per module.
- **Sparklines** — `UserController ▁▂▅▇█▇▅▂▁ (commits/week)` — temporal context in any table.

The principle: **no information loss, maximum compression.** High-level views compress but don't discard. Every summary links to its source data.

## Not Just Technical — Domain Objects That Present Themselves

Most examples lean technical: dependencies, coupling, test coverage. **The most valuable views are often domain-centric** — views where business objects present their own state, behavior, and rules in the language of the domain.

Examples of domain views:
- **Domain object state views** — "What does this Order contain? Why is it stuck in `PENDING_REVIEW`?"
- **Business rule visibility** — "Why was this payment refused? Which conditions are satisfied, which are missing?"
- **Domain algorithm step-through** — "Here's how pricing was calculated for THIS customer, step by step."
- **Domain navigation chains** — Order -> Lines -> Product -> Stock -> Restock Rules -> Supplier
- **Domain language consistency** — Where does "Customer" vs "User" vs "Account" vs "Client" appear for the same concept?

The key insight: these views are impossible to pre-build as generic tools. They are inherently unique to each project, each domain. This is precisely why moldable development exists — to make it cheap to build the exact view that answers the exact question.

## Inspector Chain Navigation (The Hard Problem)

The most important design decision is the **navigation model**: how does "this controller" link to "its service dependencies" link to "their interface definitions" link to "the tests that cover them"?

Without good entity linking, you have a dashboard. With it, you have a moldable environment.

Design decisions:
- What entity types exist? (classes, functions, endpoints, configs, tests, migrations...)
- What relationship types exist? (calls, implements, injects, tests, configures...)
- How are entities identified? (fully qualified name, file path + line, unique ID...)
- How does the viewer discover available views for an entity type?

At different output modes:
- **Terminal views:** Navigation is implicit — follow the output, grep for the next entity.
- **Web views:** Navigation is explicit — hyperlinks between entity views, click-to-drill-down.
- **Domain playgrounds:** Navigation is interactive — select an entity, explore its behavior.
- **Live view coding and above:** Navigation is semantic — the compiler model knows relationships, views generate links automatically.
